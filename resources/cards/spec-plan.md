# Spec / Plan Card

建立 Goal & Verification Contract：为目标、验收、不做范围、计划改动和测试点分配
`G` / `AC` / `OOS` / `C` / `VT` ID。每个 AC 至少映射一个目标文件和一个测试点；
验证方式明确为 static、MCP / Playwright、CLI、CI、manual 或 not-verifiable，并记录执行主体。

确定目标文件/仓库、关键数据流、兼容策略、错误处理和任务顺序。方案必须能映射到 Source
和验收标准，不臆造接口、工具能力、旧数据行为或验证结果。

设计方案先区分直接原因与设计根因，或明确需求不变量；定位规则责任层，并对比表象补丁与
消除根因的最小完整方案。至少用一个同类/后续扩展场景和空值、异常、旧数据边界检查复用性、
扩展性与健壮性；不得以少改文件为由把规则留在错误层，也不得为假想复用扩大公共改造。

标准业务流程生成正式 Spec 时才读取深度 Spec/Artifact 参考并落盘最小追踪包。实施前确认授权和脏工作区边界；UI 歧义先等待确认。
