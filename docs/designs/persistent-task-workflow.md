# 持续落盘与跨会话工作流设计

- 状态：设计提案，待评审；不是现行执行规则，也不代表以下能力已实现。
- 日期：2026-09-10。
- 范围：任务产物、工作项进度、恢复、归档、Skill 与 CLI 分工及兼容迁移。
- 本轮交付：完成现状盘点和设计收敛；不修改运行逻辑、宿主配置或现有任务数据。
- 已确认的优先级：用户选择先完成持续落盘与恢复，项目规格管理后续单独实施。

## 1. 设计结论

以任务目录为持续维护的工作档案。需求、方案、实施进度、验证证据和准确停点在工作发生时落盘，新会话直接读取任务继续执行。用户不需要在离开前专门发起交接，也不需要维护文件或记住内部命令。

借鉴 OpenSpec 的产物驱动方式，保留本仓库已有的路由、验证契约、授权边界和公开 CLI。复用现有 `spec.md`、`plan.md`、`verification.json`，不引入另一套 proposal/design/tasks 状态系统，也不嵌入 OpenSpec 运行时。

落盘和加载分开：详细记录保存在任务目录，启动只加载当前目标、未完成工作项、阻塞、证据状态及必要文档定位符。详细不等于每次把所有历史塞进上下文。

## 2. 用户体验与范围

| 场景 | 目标行为 |
|---|---|
| 提出明确需求或修复任务 | Agent 选择路由，建立任务档案，分析和方案随工作落盘 |
| 确认实施方案 | 执行既有授权规则，按工作项实施并持续保存进度 |
| 正常结束一轮或遇到阻塞 | Agent 保存当前停点、已完成项和下一步，再回复用户 |
| 新会话指定某个任务继续 | 读取该任务，核对代码和证据，处理当前未完成项 |
| 新会话只说继续 | 先使用明确的会话任务绑定；没有绑定时按任务选择规则定位 |
| 使用宿主提供的 Skill 或快捷命令 | 调用相同的任务操作，不另建状态 |
| 明确要求交接报告 | 从现有产物生成摘要，并按需补充面向接手人的说明 |

一次纯咨询、临时搜索或开放讨论不强制创建正式业务档案；一旦进入具有明确目标的分析、方案或实施任务，相关内容应持久化。维护、分析和评审任务也记录进度，但不伪造业务 Source Snapshot。

跨会话的保证限于已成功保存的检查点。程序强制关闭可能发生在代码写入和记录更新之间，恢复必须识别差异，不能声称每次编辑都被原子记录。

新会话仍需通过任务请求或宿主入口发起工作。Skill 不是监听所有聊天的后台服务；不要求特殊的“交接”口令，也不承诺自动读取其他聊天。换机器需要迁移任务产物与代码；本设计不提供自动同步服务。

## 3. 现状与根因

| 已有机制 | 核实到的实现 | 对收敛的影响 |
|---|---|---|
| 保存策略 | [产物规范](../12-artifacts.md) 默认 Conversation 留在对话；正式 Spec 是落盘例外，Micro 为持久化需升级 | 持久化应成为任务默认行为，与业务风险分开 |
| 阶段 Gate | [任务路由校验](../../src/core/task-route-guard.ts) 已要求标准实施前有非空 source/intake/spec/plan，与“Plan 仅在聊天”的说明冲突 | 统一规范、阶段卡、CLI 和测试，不能只添加一句自动保存 |
| 任务清单 | [Plan](../04-plan.md) 已定义 T 项、勾选、完成条件和 G/AC/C/VT 引用 | 增加解析和更新能力，复用 plan，不再新增 tasks 清单 |
| 需求与验证 | [验证契约](../verification-contract.md) 和 [Schema](../../resources/schemas/verification-contract.schema.json) 已定义 G/AC/OOS/C/A/VT | 保留结构化事实源，补工作项关联和证据有效性 |
| Micro | [路由定义](../../resources/routes.json) 有意图相关 stagePaths，但无 taskFlow；Brief 只允许放入 runtime/briefs | 需要任务化和持久化输入，不能仅复用现有 next |
| 阶段恢复 | [next](../../src/core/workflow-next.ts) 从 manifest 当前阶段推导 Packet；blocked 时拒绝 | 扩展为先诊断再返回允许动作，仍不自动推进阶段 |
| 运行连续性 | [route](../../src/core/route.ts) 从最近 90 天、匹配 routesVersion 的 runtime 事件校验 Run | 必需的连续性记录不能依赖可清理日志 |
| 实施中的增量状态 | [Brief 校验](../../src/core/micro-brief.ts) 要求 Implement 中实际改动和证据为空 | 必须区分首次进入实施与恢复实施，允许真实进度增量保存 |
| 交接摘要 | [摘要收集](../../src/core/task-handoff.ts) 主要读取 manifest、notes、契约和部分 source，没有直接覆盖 spec/plan/review | 常驻产物必须成为恢复的直接输入 |
| 并发保护 | [状态更新](../../src/core/task-state.ts) 已有锁、预期时间戳和单文件原子替换 | 可复用，但不能误称已保证跨文件事务 |

根因是“阶段执行”“产物保存”“接手恢复”采用了不同的完整性标准。增加更长的交接模板无法解决日常内容未保存、工作项不可解析和临时日志丢失的问题。

## 4. 吸收 OpenSpec 的边界

| 吸收 | 本仓库的实现方向 |
|---|---|
| 变更目录承载上下文 | 沿用配置中的 tasksRoot 和 Task ID |
| 产物依赖决定准备情况 | 在现有路由契约中声明所需产物与校验器 |
| 实施时逐项更新 | 将现有 plan T 项变成可解析工作项 |
| Skill 查询状态再执行 | 统一读取 CLI 的诊断与上下文结果 |
| 当前规格与任务历史分离 | 后续增加项目规格沉淀，保留原任务证据 |

不照搬完整命令体系，不把文件存在等同于内容合格，不把勾选等同于验证通过，不删除已有授权与评审边界。产物依赖是准备情况；阶段仍由既有生命周期控制，不再添加一个全局阶段引擎。

## 5. 唯一事实源

“唯一”以信息职责为单位，不要求把所有内容放进一个大文件。

| 信息 | 唯一维护位置 | 其他位置如何使用 |
|---|---|---|
| 任务身份、Route、当前阶段、阶段阻塞、仓库逻辑绑定 | `manifest.md` | CLI 与报告读取；阶段只通过生命周期命令变更 |
| 用户或 Provider 提供的原始事实 | `source.md` | 分析引用，不把推断反写为原始要求 |
| 已整理目标、验收、排除范围、计划及实际改动、VT 及其执行基线 | 标准任务的 `verification.json`；Micro 的 `brief.json` | 每个任务只选一种活动契约；Markdown 引用 ID 或生成阅读视图 |
| 技术方案、权衡与决策依据 | 标准任务的 `spec.md`；Micro 的 `plan.md#Approach` | Resume 和交接引用，不维护第二份方案正文 |
| 工作项顺序、依赖、进度、完成条件 | `plan.md` 的 T 项 | CLI 解析；不新增 `tasks.json` 或另一份可编辑任务清单 |
| 具体评审发现、处理结论、测试缺口 | `review.md` | 契约只保留验证事实；不擅自增加 Schema 未定义的 review 字段 |
| 当前停点、待判断事项、失败尝试、必读上下文 | `manifest.md` 的 Resume 与补充章节 | 保存当前有用结论，不复制完整执行日志 |
| 检查点版本、当前观察指纹、路由连续性 | `checkpoint.json`，由 CLI 维护 | 提供一致性诊断，不生成成功结论或授予权限 |
| 人读验证结果、实际改动汇总 | `verify.md`、`change-summary.md` 的生成部分 | 从契约生成，附加解释不得独立改变 VT 状态 |
| 交接报告 | `handoff.md`，可选生成视图 | 过期时重读原始产物；无此文件仍能恢复 |

`manifest.md#Scope` 可保留简短索引。正式契约建立后，目标和验收正文以契约为准；发现摘要冲突必须修正，不能以修改时间猜哪份要求有效。Intake/PRD 保留来源分析和产品背景，不各自维护验收状态。

每次契约计划修订保留修订原因与旧版本定位，完成证据绑定当时的计划版本。历史版本是历史，不与活动版本并列为当前事实源。

## 6. 产物规模与创建时机

沿用 `.agent-workflow/tasks/local/<task-id>/` 默认路径，实际位置始终由配置解析。

| 类型 | 实施或执行前的必要产物 | 按阶段增加 |
|---|---|---|
| 标准业务任务 | manifest、source、intake、spec、verification、plan | 条件需要的 PRD、review、验证证据及生成报告 |
| Micro 业务任务 | manifest、简版 source、brief、精简 plan | 精简 review、验证证据；无需正式 Spec/PRD |
| 分析、评审、维护任务 | manifest 与可交付工作项；已有独立设计文档可引用 | 对应分析、设计或评审结果；不创建虚构业务输入 |
| 所有已开始执行的持久任务 | CLI 生成的 checkpoint | 可选 handoff；不会为未到达阶段建空文档 |

Micro 和 Standard 暂不强行统一 JSON 字段。读取层提供统一目标、验收、改动和测试点视图；写入仍遵守任务所选契约，保留现有语义与枚举。Micro 升级时保留 Task ID、来源、T 项与历史，显式转换契约并核对 ID；旧 Brief 标为历史，不继续双写。

文档大小按任务需要裁剪，不能通过减少关键事实达到精简。Micro 只有少量 T 项和短方案，但必须有验收、完成条件、验证和停点。是否落盘不再成为升级 Standard 的条件，风险扩大仍按原 Gate 升级。

## 7. 工作项契约

保留现有 Markdown 清单，用稳定 T ID 表示交付单元，不用文件数或通用阶段名充当任务拆分。标准文件级 C 仍表示计划改动，一个 T 可关联多个 C。

示例为目标格式，尚未实现解析器：

```markdown
---
plan_version: 1
task_id: example-change
---

## Work Items

- [x] T1: 实现主题偏好读取
  - Stage: Implement
  - Planned Change: C1
  - Verify: VT1
  - Depends On: none
  - Done When: 合法偏好能恢复，非法值回落到默认值
  - Evidence: VT1

- [ ] T2: 接入主题切换入口
  - Stage: Implement
  - Progress: active
  - Planned Change: C2
  - Verify: VT2
  - Depends On: T1
  - Done When: 切换后页面生效，刷新后保持
  - Checkpoint: 事件绑定已完成，刷新恢复尚未核实
```

规则：

- `[x]` 表示工作项完成；未勾选项使用 `Progress: pending / active / blocked`。已勾选项不能再带冲突的 Progress，未勾选且省略时按 pending 处理。
- T 的 C/VT 引用必须存在；分析、评审等非代码项可以使用明确的交付物定位符代替 C/VT，不为凑字段创建虚构记录。
- Stage 必须属于当前任务路由；next 先确定 manifest 阶段，再从该阶段选可执行 T，不能因跨阶段依赖已满足而越过 Gate。
- 依赖不能自引用或形成环。首期同一个任务只允许一个 active 工作项，跨任务可独立执行；不据此限制执行内核内部的并行节点。
- 完成一个 T 时核对 Done When、依赖及所需证据，然后立即保存。实现项不必等待后续整体集成测试，但其自身完成条件所要求的验证必须满足。
- 工作项完成、阶段完成、整体验收完成是三个不同判断。不能由全勾选自动完成 Verify，也不能因任意一个局部测试通过而完成 T。
- 工作项阻塞记录在 T 项；如果阻止当前阶段继续，CLI 同步设置 manifest 阶段 blocked。CLI 诊断这些关系，不允许状态相互矛盾。
- 不再默认生成含未授权 commit/push 的待办。只有授权范围包含相应动作时才建立对应工作项。
- 经明确范围修订移出的 T 放入 `Deferred Work Items`，保留 ID、原因和后续定位，不计入活动进度；同步处理其 AC/VT，不能仅移动勾选项来掩盖未通过的验收。

CLI 通过 Markdown 结构解析及独立数据 Schema 校验 T 项，避免用宽松字符串匹配猜测状态。人工改文档仍可行，修改后必须校验，不能绕过证据规则。

## 8. 持续落盘协议

| 触发点 | 写入内容 | 后续检查 |
|---|---|---|
| 明确任务目标 | 身份、来源、初始范围、未知项和路由分类事实 | 不能补造用户未提供的事实 |
| 完成分析或方案修订 | 方案、G/AC/C/VT、T 项及待确认决定 | 关系完整、范围明确，应用原有实施授权规则 |
| 完成一个工作项 | 勾选、实际改动、证据与当前停点 | 工作项完成条件与证据基线有效 |
| 测试、评审得到新结果 | 原始证据引用、VT 或 Findings、影响范围 | 结果不能来自模板或预期输出 |
| 阻塞或正常结束一轮 | 未完成动作、准确停点、必要环境、下一步 | 从文件即可定位接下来要做的事 |
| 阶段转换 | 阶段产物、manifest 与 checkpoint | Gate 成功后才能发布完成状态 |

首期采用单任务串行写入、预期版本比较和可检测的检查点发布，不构建事件溯源平台。CLI 在锁内校验读取版本，写入受影响文件，最后发布新的 checkpoint；单个文件继续使用原子替换。非 CLI 的文档编辑在下一次检查时表现为待核对变化。

跨文件写入不是整体原子事务：中途失败时，文件可供检查，但新完成结论不能视为已发布。恢复报告不一致文件，核对已写代码和证据后修复记录，不自动重做可能产生外部副作用的步骤。

已发布修订检查必须用于所有阶段准入、工作项完成和生命周期写入，包括直接调用 `route --task`、`task advance` 和 `task complete`。这些入口共用校验器，不能只在 summary/next 检查；检测到未完成发布时仅允许诊断和受控修复，不根据新写入的 manifest 继续推进。

checkpoint 记录两类信息：

- 观察基线：本次保存看到的产物及仓库指纹。
- 路由记录：Task/Run/Parent Run、Route 与版本、分类事实、必要的阶段校验记录和计划绑定。

证据绑定与结果保存在同一活动契约内。标准验证契约版本 2 增加 `executedAgainst`，关联执行时间、仓库执行基线、验收/验证定义哈希和环境说明；Micro 在自身 Brief 的下一版本表达相同语义。具体字段由对应 Schema 定义，不向现有严格版本静默加字段。旧结果没有基线时按 unknown 读取。

启用新契约版本与升版属于同一次交付：`routes.json` 的 `verificationContract.version` 与执行基线启用时间、`docs/verification-contract.md`、`docs/03-spec.md` 的 frontmatter 示例、产物校验器和完成门禁必须一起更新。只加 Schema 与代码而不同步启用配置，会让按现行配置写出的版本 1 契约在持久任务里既无法登记执行基线，也无法通过 Verify。版本 1 任务继续可读；升级为持久任务前先升级契约版本并重新记录证据。

文件哈希用于一致性检测，不是授权证明。重新保存 checkpoint 只能更新观察基线，不能把旧的 passed 证据绑定到新代码上。版本不一致的证据展示为“历史通过，当前待核对”，保留原始结果和基线；重新验证，或经有依据的适用性评估建立单独关联记录后，才参与当前完成判断。

CI 沿用现有公开证据契约，通过证据文件哈希、check ID 和 commitSha 引用。HEAD 一致但工作树有未提交变更时，不能把 CI 结果当作当前改动已通过。原始 CI 证据不因摘要刷新被修改。

## 9. 恢复与任务选择

所有继续入口共用一个诊断过程，先读后写：

1. 明确目标：用户指定 Task ID 或唯一任务名称、会话已绑定任务优先；显式目标无效时直接报告，不回退到别的任务。
2. 无绑定时选择最近有持久化活动的未完成任务。同样最近时展示名称、目标摘要和阶段让用户选择；其他任务记录损坏时报告具体记录，不悄悄忽略。
3. 加载 manifest、当前方案索引、未完成 T、阻塞、当前契约和检查点，展开本次动作依赖的文档与证据。
4. 只读核对实际仓库、工作树绑定、计划版本和证据有效性。代码是当前实现事实，需求由当前契约定义；二者冲突需要分析，不能一概用代码覆盖需求。
5. 返回允许动作及原因：补产物、核对差异、等待必要决定、解除已解决阻塞，或执行下一个 T。
6. Agent 在当前授权内执行；阶段转换仍走生命周期 API，不由摘要加载或 next 自动推进。

Task ID 才是持久身份。会话 ID 可以成为宿主可选绑定，不进入通用任务契约的必要字段。不建立全工作区共享的 current-task 指针，避免多个会话互相改目标。

Worktree 逻辑绑定和基线提交属于持久任务，本机绝对路径仍留在本机映射。换机器或 runtime 映射缺失时，先核对实际 Git 状态再重绑定；不能仅因任务目录存在就在当前目录实施。

任务活动时间来自成功保存的任务修订。读摘要、生成 handoff 或宿主查看任务不应让它成为新的“最近工作任务”；旧任务无修订记录时兼容现有时间字段，并明确其来源。

恢复不依赖 handoff，也不依赖 runtime 观测日志。任务自己的版本化路由记录用于恢复连续性，CLI 仍需用当前支持的规则重校验。缺记录或版本不兼容时给出迁移/重评估动作，不凭 manifest 当前阶段伪造已通过 Gate 的历史。

运行日志可清理不等于执行内核的事件日志可随意删除。本轮方案解决任务级恢复；已有 execution run 的进程、节点、锁、外部动作恢复仍由执行内核管理。任务产物通过公开契约引用其证据，不用 plan 勾选替代内核完成事件，也不自动重启丢失状态的运行。

## 10. Router、Skill 与 CLI

| 层 | 保留和新增职责 | 不承担的职责 |
|---|---|---|
| Router / Profile | 选择路由、产物要求和能力；控制按需加载与预算 | 不写长篇产物模板，不维护另一套任务进度 |
| Skill / 阶段卡 | 分析事实、维护文档、执行 T、解释阻塞，落实持续保存 | 不自行推断 CLI 可确定的状态，不承诺后台自动保存 |
| CLI / Schema | 建任务、解析契约、更新工作项、检查证据和版本、诊断 next、管理生命周期 | 不编造需求、技术决策或验证结论 |
| 宿主 Adapter | 将自然语言、Skill 或快捷入口映射到同一任务操作 | 不持有唯一业务状态，不复制工作流长规则 |

不新增一套平行的 apply/continue/complete 引擎。建议扩展现有 `task` 和 `next` 命令族，具体新增参数在实现契约中确定：

- 初始化或识别持久任务，返回固定 Task ID。
- 读取状态与下一步诊断，兼容文本及 JSON 输出。
- 校验/更新 T 项及其证据，发布 checkpoint。
- 继续使用现有 start/advance/block/resume/complete；prepare/handoff 保留为可选报告入口。

Profile 通过抽象能力绑定 Skill，Core 不写死具体 Skill 名。没有 Skill 自动发现能力的宿主仍可读取 Packet 中的文件执行。关键动作前后的保存要求应由路由明确加载，不依赖 Agent 偶然命中 Skill description。

## 11. 阶段结束与返工

依赖检查不代替生命周期。进入 Implement 检查活动计划和授权；离开 Implement 检查计划中的实施工作项及实际改动；Review 检查 Findings 处置；Verify 核对所有必需 AC/VT 及有效证据。

无法验证的必需条件不能被标记为通过。若用户明确接受范围缩减或延后，记录具体项、原因和后续任务，保持 conditional 等真实结果，不能通过归档把它们变成 verified。最终完成政策在版本化 Gate 中统一声明，模板不再单独定义。

发现新风险或设计错误时修改同一个任务的活动计划，保留修订原因和受影响 T/VT。当前生命周期没有完整的回退协议，P1 必须提供 Standard 最小受控重开，使 Review/Verify 中发现的问题能合法回到必要阶段；P2 再扩展 Micro 和跨路由修订。不能让 Agent 直接改 Current Stage 冒充已有支持。范围与批准方案发生变化时执行既有重新确认规则，未受影响的证据保留但需满足有效性要求。

实施授权绑定稳定的计划投影，工作项进度、实际改动和新证据不进入这个计划哈希。Micro 现有“Implement 证据必须为空”的约束应改为首次准入校验；在同一阶段恢复时允许已有实施记录，并检查其真实性和计划一致性。范围、目标文件或验收变化时走计划修订，不能通过换 Run 来避开旧计划绑定。

恢复也不应机械要求用户重复批准同一方案。任务记录批准的动作、范围、计划哈希、来源及边界，接手时结合当前用户请求和工具权限判断其是否仍适用；缺少可核实授权、存在冲突或计划变化时才询问。仅有文档中的“已批准”不是授权证明，Git 和外部操作继续独立判断。该行为不取消当前会话确认：进入 Implement（`advance` / `reopen`）与激活工作项（`task item --status active`）都必须由当前会话用户确认并附 `--user-approved`，批准依据写入 `--approval-source` 且不得使用占位文本；记录中的批准只决定是否需要重新展示实施方案，不替代当次确认。

## 12. 归档与项目规格

任务档案回答“这次为什么改、完成了什么”；项目规格回答“当前系统应具备什么行为”。任务 `spec.md` 是技术设计，不直接升级为项目规格。

分两步落地：

1. 本地归档先采用任务内归档元数据和只读查询视图，保留原目录与证据引用。归档独立于 Git 发布，不通过移动目录制造路径失效；归档不能更改验收结果。
2. 后续通过可配置的项目规格目录维护长期行为要求。默认建议 `.agent-workflow/specs/`，与忽略的任务目录、知识候选和 runtime 分离。由当前验收要求整理规格变更草案，记录来源、适用代码版本、增改删操作和验证状态。

同步现行规格前重新检查目标规格基线。并发任务改同一条需求时必须显式合并，不能最后写入者覆盖；未验证或未落地的能力保留为草案，不描述成已经生效。任务完成、代码合并/部署和规格生效不是同一个状态。

项目规格允许未来按宿主治理策略版本化，但本地任务数据继续遵守现有禁止提交约束。归档、生成规格草案都不自动 stage、commit、push 或发布；不把原始来源正文、机器路径、凭据复制进共享规格。

## 13. 兼容与迁移

- 新任务启用版本化的持久化产物配置。`Conversation / Portable` 老任务继续可读，不用全量改写历史来启动新版本；新恢复契约不得隐式依赖 Portable 必有 handoff。
- manifest 的任务新字段通过新 Schema 版本加入；checkpoint 使用独立 Schema。验证契约和 Brief 增加执行基线时各自升版，继续兼容读取版本 1，禁止向严格 `additionalProperties: false` 的旧版本静默加字段。升版必须同时更新版本化启用配置（`routes.json` 的版本与启用时间）、产物规范和门禁；缺少启用时间时，按旧配置产出的旧版本契约会形成无法收口的任务。
- 标准任务优先复用已有 Spec 包，补 plan 可解析字段、直接恢复上下文与检查点。信息缺失标 unknown，不从“阶段 complete”推断 T 或 VT 已完成。
- Micro 在补齐 taskFlow、变更意图绑定、Brief 持久路径和路由连续性后再启用默认落盘。不能只把 runtime 文件复制到任务目录而不修正 Gate。Brief 目前被 `workflow-input.ts` 的 allowedPrefix 限制在忽略目录 `.agent-workflow/runtime/briefs/`；迁移到任务目录前必须同时登记产物契约、把它排除在 `runtime/*` 清理与 `.gitignore` 规则之外，否则"持久化"只停留在复制文件这一层。P2 之前 Micro 继续使用 runtime 工作副本，不因为需要保存而升级 Standard。
- 旧 handoff/notes 保留可读。恢复时将仍有效的决策、停点和失败尝试整理到对应活动产物并记录来源；无需删除历史 notes。新摘要不依赖其完整性。
- 旧 handoff-state 只校验对应旧报告；新的任务 checkpoint 独立版本化。不能直接改文件名假装继承了更强的证据保证。
- 原有任务只有 runtime 日志时，校验日志、产物与当前代码后建立迁移记录；日志已丢失就标缺口，不能补造授权或成功事件。日志超期或已被清理时，只有用户明确确认的重建迁移才被接受，检查点标记 `reconstructed`，诊断以 warnings 报告该缺口而不阻断后续阶段；重建迁移不恢复任何历史 Gate 结论。
- 未知未来版本返回可操作的兼容错误；已有文件不被破坏。迁移前后可比较内容与版本，失败不删除原记录。
- 宿主需要消费升级后的包与产物契约，检查 bootstrap 是否仍指向实际 START。只更新托管入口和必要配置，保留自定义 Profile；不要求复制整份 Skill 或修改业务源码。

## 14. 实施顺序与验证

| 阶段 | 交付内容 | 完成标准 |
|---|---|---|
| P1：标准任务完整恢复 | 保存策略统一；plan 解析；检查点与连续性；验证基线与失效检测；全部入口共用发布校验；直接恢复 spec/plan/review；授权核对与最小受控返工 | 不执行交接也能跨会话继续；清理观测日志仍可恢复；刷新检查点不改变旧证据有效性 |
| P2：Micro 与返工 | Micro taskFlow 与持久 Brief；实施中增量保存；与 Standard 的显式转换；计划修订和受控重开 | Micro 不因保存而升级；变更后旧通过结论不能继续冒充有效 |
| P3：归档与宿主收敛 | 本地归档；宿主快捷入口和能力绑定完善；旧产物批量迁移工具 | 多入口选中相同任务且只维护一份状态；旧任务无破坏性迁移 |
| P4：项目规格沉淀 | 规格草案、基线比较、同步及冲突处理 | 任务历史与当前规格分离，未验证内容不会自动成为现行规则 |

P1 先形成一个完整可用闭环，不把必要恢复记录推迟到后续。P2 完成后才宣称所有编码路线都默认支持持续落盘。P4 不阻塞当前用户最需要的跨会话体验。

P1 同时包含现有托管入口可读取新规则的兼容检查、一个代表性宿主验收，以及单个旧任务的按需迁移。P3 扩大分发和批量迁移能力，不把首批用户的可用性推迟到第三阶段。

实施时必须覆盖以下验收场景：

| ID | 场景 | 预期 |
|---|---|---|
| V1 | 完成 T1 后正常结束会话，未调用交接 | 新会话直接定位 T2，并读取需求和方案 |
| V2 | 代码已写、checkpoint 发布前进程中断 | 报告差异，核对后恢复；不重复盲目写入 |
| V3 | 用户或另一个会话改变代码 | 旧证据保持历史绑定，当前结果需要重评估 |
| V4 | 两个任务并存、一个报告刚重新生成 | 读报告不改变最近工作任务；明确 ID 始终优先 |
| V5 | 同任务并发写入或计划文件被人工编辑 | 预期版本冲突可检测，不覆盖新内容 |
| V6 | 所有 T 勾选，但必需 VT 失败或证据过期 | Verify/最终完成不得被错误放行 |
| V7 | 清理 runtime 观测日志或升级 routesVersion | 支持的任务凭持久记录重校验；不兼容时明确给迁移动作 |
| V8 | Micro 无正式 Spec，随后需要跨会话或升级 | 保持轻量记录；升级时 Task ID 和事实关联不丢失 |
| V9 | 只有旧 handoff 或 Spec v1，缺少详细进度 | 保留历史，显示缺口，不伪造完成证据 |
| V10 | 当前阶段 blocked，新会话请求继续 | 能诊断阻塞，解决后显式解除，不自动跳过 |
| V11 | 正文或证据超出上下文预算 | 当前工作所需信息可定位展开，不从中间截断 |
| V12 | 两个任务同时更新同一项目规格 | 基线冲突被发现，不静默覆盖 |
| V13 | 执行内核运行暂停但 T 被人工勾选 | 内核仍保持真实暂停状态，不自动重放外部动作 |
| V14 | 同一批准计划跨会话继续，或批准范围发生变化 | 前者核实后直接继续；后者只询问变化所需的决定 |
| V15 | Micro 在 Implement 阶段已有实际改动与验证记录 | 可保存和恢复，不为满足旧 Gate 清空真实证据 |
| V16 | CI 对应 HEAD 通过，本地另有未提交修改 | CI 保留历史结果，不把未覆盖改动判定为通过 |
| V17 | checkpoint 发布中断后直接调用 route/advance/complete | 与 next 一样拒绝继续推进，只允许诊断和受控修复 |
| V18 | Standard 已在 Verify，恢复发现需修改代码 | P1 即可受控重开必要阶段，保留旧证据及修订原因 |

## 15. 本次已收敛的决定

1. 任务从开始执行就落盘，持久化与业务复杂度解耦。
2. 复用现有产物和 G/AC/C/A/VT，不整体合并 OpenSpec，不新增重复任务状态。
3. plan 的 T 项是工作项进度事实源，manifest 是阶段事实源，契约是验收与验证事实源。
4. 恢复直接读取常驻产物；handoff 保留为可选报告。
5. 必需连续性记录属于任务，观测日志不承担恢复前提；内核事件仍归内核管理。
6. Skill 组织工作，CLI 决定可计算状态，Router 负责加载；宿主入口可不同，状态必须相同。
7. 先完成持续记录与可靠恢复，再做归档和项目规格沉淀。

后续实现需细化版本化 JSON 字段、CLI 参数和迁移算法，但以上信息归属与行为边界不应再次分叉。本提案的评审通过只确认设计方向；代码实施、宿主升级和 Git 发布分别按实际授权范围执行。
