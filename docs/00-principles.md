# Principles

## 核心原则

- 先理解，再实现。
- 业务任务先完成 Source Capture：Pool Entry 读取本地需求池/缺陷池，Direct Entry 保存用户粘贴原文，再进入 Intake。
- 先定位，再修改。
- 先明确产物，再进入下一阶段。
- 信息不足时，提出最少必要问题。
- 不修改无关代码。
- 不做无关重构。
- Review 与实现视角分离。
- 验证结果必须记录，未验证项也必须记录。
- 工具能力是增强项，流程协议必须稳定。
- 事实保存在仓库规则和 Portable 任务产物中，不依赖聊天记忆。
- 工具适配器只映射能力，不产生项目规则。
- 规则文件按代码治理：可审查、可追踪、可迭代。
- 自主执行越强，门禁越要硬。

## 默认工作方式

1. 从用户输入提取事实，不把猜测写成结论。
2. 识别任务类型：需求、缺陷、重构、评审、调研、文档、Git 操作。
3. 根据任务复杂度决定是否需要完整 PRD/Spec。
4. 对低风险小改动可以压缩文档，但不能跳过理解、定位、review、verify。
5. 对高风险或跨模块改动必须完整执行所有阶段。

## 阶段门禁

| 门禁 | 触发点 | 通过标准 |
|------|--------|----------|
| Pre-Implement | 写代码前 | 已定位文件，已明确目标行为，歧义已澄清 |
| Post-Edit | 每轮修改后 | 自审通过，无明显规范违背，无无关改动 |
| Pre-Commit | 提交前 | diff 已检查，项目允许的验证已完成，未验证项已说明 |
| Pre-Push | push 前 | 用户允许 push，当前分支和远端目标明确 |

## Human-in-the-loop

以下场景必须停下来让用户确认：

- 需求或缺陷描述存在关键歧义。
- UI 截图、样式对比、业务口径需要人工判断。
- Spec 涉及跨模块、接口、数据结构或旧数据兼容。
- 实现需要删除数据、迁移数据、批量改文件或重构公共逻辑。
- Review 发现 P0/P1 问题但没有低风险修复方案。
- stage、commit、push、创建 PR、发布、合并等写入 Git 历史或影响远端的动作。

## 工具降级

- 支持 MCP 时，优先按需检索规则、文档、需求和知识。
- 不支持 MCP 时，读取仓库内 Markdown 规则文件。
- 不支持 Skill 时，按项目策略登记的路径读取 `SKILL.md` 及其引用文件。
- 不支持文件读写时，要求用户粘贴上下文，并输出可应用 patch。
- 不支持命令执行时，列出人工命令和预期检查点。
- 不支持 subagent 时，由当前执行者串行完成对应职责。
- 不支持自动加载仓库规则时，使用 adapter 或 README 中的启动提示显式加载。
- 工具切换时，不继承未写入任务产物的完成状态、验证结果或 Git 授权。

## 规则治理

- 每个规则文件只覆盖一个主题。
- 规则要包含适用场景、禁止事项和正反例。
- 修改规则也要 review，不能把临时结论直接沉淀为长期约束。
- 高频错误优先沉淀为规则，低频一次性判断保留在任务记录。
- 规则冲突时，项目内规则优先于个人规则，用户最新指令优先于默认流程。
