# PRD

PRD 的目标是明确产品层面的目标、范围和验收标准。它不要求冗长，但必须让实现和验收有共同依据。

## 适用场景

- 新功能
- 行为变更
- 跨页面或跨模块改造
- 复杂缺陷，尤其是涉及业务规则或 UI 交互的缺陷

小范围纯技术修复可以生成简版 PRD。

## 输出模板

```md
# PRD

## 背景
为什么要做，当前问题是什么。

## 目标
完成后用户或系统得到什么能力。

## 用户场景
描述主要使用者、入口、操作路径和结果。

## 功能范围
本次要做的内容。

## 不做什么
明确排除项，防止范围扩张。

## 交互规则
页面、按钮、弹窗、表格、提示、禁用态、空状态等。

## 数据规则
字段来源、校验、默认值、保存逻辑、旧数据兼容。

## 异常规则
失败提示、重试、权限不足、网络异常、空数据。

## 操作日志
需要记录的关键操作、人员、单据、时间和原因。

## 验收标准
- 
- 

## EARS 验收标准
- WHEN [condition/event]
  THE SYSTEM SHALL [expected behavior]
```

## 通过标准

- 目标和范围清楚。
- 验收标准可验证。
- 已说明不做什么。
- 交互和异常规则不留关键空白。
- 涉及旧数据时有兼容说明。
- 至少包含一组可直接转成测试用例的验收标准。

## EARS 写法

推荐用 EARS 让需求可测试：

```text
WHEN 用户提交必填字段为空的表单
THE SYSTEM SHALL 在对应字段显示校验提示，并阻止保存
```

常用模式：

- `WHEN <事件> THE SYSTEM SHALL <行为>`：事件驱动。
- `WHILE <状态> THE SYSTEM SHALL <行为>`：状态持续期间。
- `IF <条件> THEN THE SYSTEM SHALL <行为>`：条件分支。
- `WHERE <范围> THE SYSTEM SHALL <行为>`：指定范围。
