# Execution

Execution 的目标是用消除根因的最小完整语义闭环完成实现，并保留可审查轨迹。

## 写代码前

- 已阅读相关规则和项目策略文件。
- 已定位目标文件。
- 已理解现有模式。
- 已明确本次不改哪些内容。
- UI 或业务语义存在歧义时，先确认。

## 修改原则

- 优先沿用现有模式。
- 最小化按语义闭环衡量，不按文件数或代码行数衡量。
- 不为当前案例复制规则、状态或增加孤立特判。
- 保持改动范围收敛；正确责任层超出批准范围时停止并重新评审。
- 不重排无关代码。
- 不做无关格式化。
- 不引入无关依赖。
- 不覆盖用户已有改动。
- 增量代码遵守项目当前语法和规范。

## 代码安全

- 事件监听要考虑解绑。
- 定时器要考虑清理。
- 异步回调要考虑组件销毁后的状态。
- DOM 或组件引用要考虑生命周期。
- 按钮和长耗时操作要考虑重复点击。
- 输入、接口结果和权限数据要考虑空值。

## 修改后

从任务专属 diff 更新 Actual Change Inventory，再输出简短变更说明：

```md
## Change Summary
- 修改了什么
- 为什么这样改
- 影响哪些文件
- 是否有未验证项

## Actual Change Inventory
| Actual ID | Repository | File | Summary | Planned Change | Acceptance |
|-----------|------------|------|---------|----------------|------------|
| A1 | | | | C1 | AC1 |
```

## 通过标准

- 改动与 Spec 一致。
- 修改位于正确责任层，能够覆盖已确认的同类、扩展和异常边界。
- 没有无关文件或无关格式化。
- Actual Change 与任务专属 diff 一致，并能追踪到 C 和 AC。
- 已记录验证方式。
- 已进入 Review 阶段。
